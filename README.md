# Transcribe Local

**四台听力互不相同的本地引擎转同一段录音，分歧交给一个大模型定字。**

**音频不出本机。** 最后那步定字可以接一个 API，也可以用本机模型、全程离线。

[Transcribe Labs](https://transcribe.solutions) 出品 · [在线版](https://transcribe.solutions)

## 它做什么

把一段中文访谈录音，在本机变成一份带说话人、带时间戳、标了存疑处的转录稿。

**先把「本机」说清楚，别让你事后才发现：**

| 这一步 | 在哪跑 |
|---|---|
| 转码 · 声纹分段 · 四路 ASR | **全在你的机器上。音频和模型一个字节都不出去。** |
| 最后一步「融合定字」 | 两条路，你选：**①** 接一个说 OpenAI 协议的 API（默认，便宜、效果稳）—— 这一步会把**转录文本**发给你选的那家，音频仍然不发；定不下来的专有名词还会作为**搜索词**发给博查联网核实（只是几个词，不是稿子；不设密钥就自动不联网）；**②** 用本机大模型，**全程离线**，一个字节都不出这台机器。 |

要「数据一个字节都不许出机器」，就走 ②，改一行 `base_url` 的事。

单台开源 ASR 转中文访谈，错得比你想象的多。这个项目的做法是让**四台解码路线互不相同**的引擎
听同一段音频，用代码穷举定位它们写法不一致的地方，再交给一个大模型逐处定字 —— 定不下来的就地标 `[❓]`，
留给你复核。

```
音频
 └─ 声纹分段（pyannote-segmentation-3.0 + CAM++）+ VAD 补漏 → 18 秒切块
     │
     ├─ FireRed-ASR2      AED 自回归
     ├─ Zipformer-CTC     CTC 逐帧          四路吃同一份切块，
     ├─ Paraformer-2023   非自回归          块与块天然逐一对应
     └─ Qwen3-ASR 0.6B    LLM 式
     │
     ├─ 分歧册 —— 纯 Python 穷举定位各路写法不一致的片段
     └─ 融合 —— 大模型按规则 + 你的术语库定字
     │
   融合终稿
```

> 📄 **[四台耳朵，一个脑子](docs/方法论.md)** —— 这套做法怎么来的，以及一路上哪些直觉是错的。

## 它做得怎么样

我们拿一条 **37 分 51 秒的真实客户访谈**量过（人工整理稿作金标，切成 665 个语义块，
其中 461 个是实质内容、204 个是纯附和）。下面这张表里的每个数，都是**同一把尺**量出来的，
而且融合那几行是**同配置跑三遍的平均值**（2026-09-12；括号里是三遍的极差）：

| | 算问题 | 把标了 `[❓]` 的也算 | 回退 |
|---|---|---|---|
| FireRed-ASR2（四路里最好的单台） | 96 | 96 | — |
| Paraformer-2023 | 114 | 114 | — |
| Zipformer-CTC | 118 | 118 | — |
| Qwen3-ASR | 122 | 122 | — |
| 四路同时出问题（只靠投票时的天花板） | 50 | 50 | — |
| **四路 + 融合 + 术语库 · DeepSeek V4.1 Flash · 8 块一批** | **51.0**（±5） | 58.7 | 0.7 |
| 四路 + 融合 · 同上、不挂术语库 | 54.7（±5） | 64.7 | 1.0 |
| 四路 + 融合 + 术语库 · DeepSeek · 与在线版同款的两阶段工作流 | 60.3（±5） | 63.7 | 2.7 |
| 四路 + 融合 + 术语库 · Claude Opus（订阅命令行，与在线版同一条路） | 46.0（±4） | 51.3 | 0.3 |

几件事值得单独指出来：

- **最好的单台 96 → 融合 51**，砍掉 45 处；换成 Claude 那条路是 46。
- **回退接近零。** 四路都写对、融合反而改错的块：三遍平均 0.3 到 0.7 处。这是算出来的，不是感觉。
- **离天花板只差 1 处**（51 vs 50）。剩下的错里有 50 处是**四台一起听错**、正确写法根本不在选票上 ——
  换更强的融合模型也投不出来。**能靠融合拿回的，基本已经拿回了。**
- **术语库有用但不万能**：挂 11 条针对本录音的库，整体少错 4 处；库里那些词的「既没写对也没标疑」从 50 处降到 23 处，
  但没有归零 —— 四台都听不出音近残片的词，库锚不住。
- **与在线版同款的两阶段工作流在这把尺上反而差 9 处**：它润色更狠、通读定下的专名表会全篇统一写法，严格逐字比对时吃亏。
  两种工作流都在配置里（`p3.workflow`），默认值见 `config.default.yaml` 的说明。

两列要一起看。左列不把「已经标了 `[❓]` 交给你复核」的块算作错 —— 标出来的不算悄悄错。
右列一处不豁免。**只看左列会高估**：融合模型可以靠多标存疑把左列压下来，右列才是它真正定对了多少。

### 要跑多久

这台 8 核 16 G 的笔记本（纯 CPU），那条 37 分 51 秒的访谈：

| | 耗时 |
|---|---|
| P0 转码 · 声纹 · 切块 | 7 分钟 |
| P1 四路识别 | **12 分钟**（三路并行；逐台跑要 20 分钟） |
| P3 融合定字（`deepseek-flash`，8 块一批） | 10 到 11 分钟 · 25 批并发 4 · 约 0.33 美元（非高峰价） |
| P3 融合定字（`deepseek-flash`，两阶段） | 7 到 10 分钟 · 约 0.14 到 0.20 美元 |
| P3 融合定字（Claude 订阅命令行） | 18 到 43 分钟 · 走订阅额度 |

四路**默认并行**，几台同时跑由程序按你机器的核数和内存算：
`min(引擎数, (核数−1)÷每台线程数, (总内存−4G)÷最重那台)`。这台算出来 3 路，卡在核数上。
2.5 分钟的片段上实测：三路并行 P1 耗时 68 秒、逐台跑 138 秒，**省一半**，
而单台引擎的每块耗时几乎没变（3.8 s/块 vs 3.7 s/块）—— 争 CPU 的损耗很小。峰值常驻内存 2.8 G。

**大头是融合那一步**，它按批调 API，跟本机快慢无关。

### 什么算「出问题」——判据在这儿，你可以拿自己的录音复现

**上面那张表的每个数，都是仓库里 [`tools/score.py`](tools/score.py) 跑出来的** ——
你可以拿自己的录音和人工整理稿量一遍：

```bash
python3 tools/score.py 你的金标.md out/你的终稿.merged.md --terms 你的术语库.md
```

（我们那条录音是客户内容，不在仓库里，也不会公开。但工具在，判据就不是我们说了算。）

它走两道闸。**第一道看对齐质量**：金标这一块几乎原样出现在机器稿里、且没有连续两个字对不上，
直接算过。**第二道**才是下面五条，过不去的才算问题：

| | 不算问题 | 例 |
|---|---|---|
| ① | 只差语气词 / 附和词 / 儿化 | 金`哦，明白` 机`明白` |
| ② | 数字体例不同 | 金`23 年 12 月 28 号` 机`二三年十二月二十八号` |
| ③ | 的地得 / 您你 | 金`频繁地报警` 机`频繁的报警` |
| ④ | 机器自己标了 `[❓]` | 它举手说了「这儿我没把握」 |
| ⑤ | 机器写的是术语库里的词形，金标记的是同字不同序的口语说法 | 见下 |

归一之后，**金标那句必须原样出现在机器稿里**才算过 —— 不用相似度阈值。
我们第一版用了 0.88 的相似度，结果一个两字行业术语被听成了一个同音的常见单字，
夹在三十多字的长句里，整句相似度仍有 0.9+，
被当成「一致」放过了。**那种尺子会让自家产品看起来比实际好。**

### 术语库：有用，但不是挂上就有用

这次是**挂着一份 10 条的行业术语库**跑的。先说它帮上的忙 —— 机制不是凭空造词，
是**把音近的残缺候选锚回正确词形**：一个没听过的专名，四路里有三路整段听成了读音相近的常见词
（音对、字错），剩下一路给出的是这个专名的音近残片。没有术语库时，融合按票数办事、跟了那三路，
顶多补一个 `[❓]`；库里有正确写法时，那一路的残片就有了落点。
**关键是那一路必须已经给出了音近的东西**，库负责定形，不负责无中生有。

再说它没帮上的忙 —— 这次库里明明有的词，**仍然错了或丢了**：

```
库里有〈两字术语 A〉    终稿写成了一个同音的常见单字
库里有〈两字术语 B〉    终稿写成了一个音近的日常词
库里有〈四字产品名 C〉  终稿把它整个丢掉了
```

**挂了库不等于那个词就一定对。**而且它**不单调** —— 我们见过库里有那个词、融合反而写错的反例。
它提升的是期望值，不保证逐处都更好。

### 一个你得自己拿主意的取舍

受访者嘴里把一个四字术语的前两个字和后两个字**说颠倒了**（同样四个字，顺序反过来），
人工金标照实记了这个颠倒说法。我们的终稿写的是**术语库里那个正确词形**。

- 你要的是**逐字忠实**（受访者说什么就是什么）→ 这叫改了原话，是个问题；
- 你要的是**一份能用的终稿** → 这是帮忙。

上表按后者计（规则 ⑤）。**这不是 bug，是个取舍**，我们把它摆出来而不是藏起来。

**它离商用还有多远，我们也说：** 同一条录音走我们自己的云端生产线，残留不到 10 处，
而且那些残留在流程里都留了痕、都能由人工复核改掉。要 27 门语言、更高精度或团队协作，
用[在线版](https://transcribe.solutions)。

## 装

```bash
pip install git+https://github.com/ZeyuSi-2099/transcribe-local
transcribe-local setup        # 首启向导：下模型、挑融合后端
transcribe-local serve        # 起本机服务，自动开浏览器
```

还没上 PyPI，先从仓库装。Python ≥ 3.10，**CPU 就够，不需要显卡**。
整条链的第三方依赖只有两个：`sherpa-onnx` 和 `numpy`。

**融合那一步默认接 API**（`deepseek-flash` + `reasoning_effort: high`，一份 38 分钟访谈约十分钟、零点几美元），
这一档不是随手挑的 —— 它就是我们自己那条云端生产线走 DeepSeek 时用的同一个模型、同一组参数
（2026-09-10 起这个名字指向 V4.1 Flash，上面的数字就是它跑出来的），所以你不必为了跑通它先下一个几 G 的大模型。想全程离线就把 `base_url` 指到本机的
Ollama / LM Studio / mlx_lm.server / llama-server —— 同一条代码路径，再加约 4.5 GB 权重。

识别用的模型要下 **2.3 GB**、解压后占盘 **2.7 GB**（四路 ASR + 声纹 + VAD），从各自官方源下载，
**本仓库不重分发权重**。七个都是宽松许可（Apache-2.0 或 MIT），逐条来源记在
[`models/manifest.toml`](models/manifest.toml) 里 —— 但**模型的许可跟本仓库的许可是两回事**，
上游也可能改，升版本请自己重查。

嫌大就先只装一路：`transcribe-local setup --minimal`，**271 MB**，五分钟出第一份稿子 ——
只是没有多路融合，也就没有这个项目的正题。

## 调

这个软件的正题是**参数可调**，而且每个参数都告诉你「这个默认值是怎么来的」：

```
[定档]     有全长实测支撑
[未验证]   照搬上游或凭常识定的，没有实测证据
[有更好的] 已经量出更好的做法，但还没落地
[缺陷]     已知有问题，尚未修
```

全部参数见 [`config.default.yaml`](config.default.yaml)。已知缺陷也在里面明写，没有藏着。
