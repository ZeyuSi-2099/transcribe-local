# Transcribe Local

**四台听力互不相同的本地引擎转同一段录音，分歧交给一个大模型定字。**

**音频不出本机。** 最后那步定字可以接一个 API，也可以用本机模型、全程离线。

## 它做什么

把一段中文访谈录音，在本机变成一份带说话人、带时间戳、标了存疑处的转录稿。

**先把「本机」说清楚，别让你事后才发现：**

| 这一步 | 在哪跑 |
|---|---|
| 转码 · 声纹分段 · 四路 ASR | **全在你的机器上。音频和模型一个字节都不出去。** |
| 最后一步「融合定字」 | 两条路，你选：**①** 接一个说 OpenAI 协议的 API（默认，便宜、效果稳）—— 这一步会把**转录文本**发给你选的那家，音频仍然不发；**②** 用本机大模型，**全程离线**，一个字节都不出这台机器。 |

要「数据一个字节都不许出机器」，就走 ②，改一行 `base_url` 的事。

单台开源 ASR 转中文访谈，错得比你想象的多。这个项目的做法是让**四台解码路线互不相同**的引擎
听同一段音频，用代码穷举定位它们写法不一致的地方，再交给一个大模型逐处定字 —— 定不下来的就地标 `[❓]`，
留给你复核。

```
音频
 └─ 声纹分段（pyannote-segmentation-3.0 + CAM++）+ VAD 补漏 → 18 秒切块
     │
     ├─ FireRed-ASR2      AED 自回归
     ├─ Zipformer-CTC     CTC 逐帧          四路吃同一份切块，
     ├─ Paraformer-2023   非自回归          块与块天然逐一对应
     └─ Qwen3-ASR 0.6B    LLM 式
     │
     ├─ 分歧册 —— 纯 Python 穷举定位各路写法不一致的片段
     └─ 融合 —— 大模型按规则 + 你的术语库定字
     │
   融合终稿
```

## 它做得怎么样

我们拿一条 **37 分 51 秒的真实客户访谈**（人工整理稿作金标）量过。口径是
461 个实质语义块里出问题（漏或错）的块数：

| | 出问题的块 | 把标了 `[❓]` 的也算进来 |
|---|---|---|
| 最好的单台本地引擎（FireRed-ASR2） | 56 | 56 |
| **本地四路 + 融合** | **23** | 24 |
| 四路组合的理论天花板（四台都听错的） | 19 | 19 |

两列要一起看。左边那列不算「已经标了 `[❓]` 交给你复核」的块 —— 那是产品口径：标出来的不算悄悄错。
右边那列一处不豁免。**只看左列会高估**：融合模型可以靠多标存疑把左列压下来，右列才是它真正定对了多少。

可拿回的空间是 `56 − 19 = 37 处`。**零回退** —— 没有出现「单台本来对、融合改错」的情况。

> ⚠️ 这是**跑一次**的结果，不是平均值。这一步的 run-to-run 方差很大（同一份输入同一套提示词，
> 跑两次成绩能差好几处），所以别把它当精确刻度。

**它离商用还有多远，我们也说：** 同一条录音走我们自己的云端生产线，残留不到 10 处，
而且那些残留在流程里都留了痕、都能由人工复核改掉。要 27 门语言、更高精度或团队协作，
用[在线版](https://transcribe.solutions)。

**剩下的大部分是四路一起听错的** —— 正确写法根本不在选票上，换更强的融合模型也投不出来。
这些里面一多半是术语（光伏行业的专名与行话）。所以术语库是最值得先挂的东西。

**术语库能把这个「天花板」推下去。** 那个 19 的定义是「四台引擎都听错的块数」，
它成立的前提是**融合只能在四路候选里挑**。术语库违反了这个前提 —— 它是**第四条信息源**，不在四路里。
所以 19 只是「只靠四路投票」的天花板。我们挂上一份对症的术语库实测过，出问题的块数**降到 18、低于 19**
（那一次用的是提示词的一个精简变体，数字不能直接并到上表里；机制是一样的）。

机制不是凭空造词，是**把音近的残缺候选锚回正确词形**。典型形状是这样：一个没听过的专名，
四路里有三路整段听成了一个读音相近的常见词（音对、字错），剩下一路给出的是这个专名的**音近残片**。
没有术语库时，融合按票数办事、跟了那三路的常见词，顶多补一个 `[❓]`；库里有正确写法时，
那一路的残片就有了落点 —— 模型把它锚回去，写对，而且不必标疑。
**关键是那一路必须已经给出了音近的东西**，库负责定形，不负责无中生有。

**但它只在库里真有那个词时才起作用。** 我们拿一份现成的客户术语库对过，上面这些失败的词
**一个都不在库里**。术语库要写对才有用，不是挂上就有用。而且它**不单调** —— 我们见过库里有那个词、
融合反而写错的反例。它提升的是期望值，不保证逐处都更好。

## 装

尚未发布。

**融合那一步默认接 API**（`deepseek-flash` + `reasoning_effort: high`，一份 38 分钟访谈几毛钱、约 40 分钟），
这一档不是随手挑的 —— 它就是我们自己那条云端生产线走 DeepSeek 时用的同一个模型、同一组参数，
所以你不必为了跑通它先下一个几 G 的大模型。想全程离线就把 `base_url` 指到本机的
Ollama / LM Studio / mlx_lm.server / llama-server —— 同一条代码路径，再加约 4.5 GB 权重。

识别用的模型要下 **2.3 GB**、解压后占盘 **2.7 GB**（四路 ASR + 声纹 + VAD），从各自官方源下载，
**本仓库不重分发权重**。七个都是宽松许可（Apache-2.0 或 MIT），逐条来源记在
[`models/manifest.toml`](models/manifest.toml) 里 —— 但**模型的许可跟本仓库的许可是两回事**，
上游也可能改，升版本请自己重查。

嫌大就先只装一路：`transcribe-local setup --minimal`，**271 MB**，五分钟出第一份稿子 ——
只是没有多路融合，也就没有这个项目的正题。

## 调

这个软件的正题是**参数可调**，而且每个参数都告诉你「这个默认值是怎么来的」：

```
[定档]     有全长实测支撑
[未验证]   照搬上游或凭常识定的，没有实测证据
[有更好的] 已经量出更好的做法，但还没落地
[缺陷]     已知有问题，尚未修
```

全部参数见 [`config.default.yaml`](config.default.yaml)。已知缺陷也在里面明写，没有藏着。
