# 四台耳朵，一个脑子

> 我们做中文访谈转录。这篇讲的是**本机版**是怎么做的，以及一路上哪些直觉是错的。
> 所有数字来自一条 37 分 51 秒的真实访谈，人工整理稿作金标；判分工具在
> [`tools/score.py`](../tools/score.py)，你可以拿自己的素材复现。

## 一、单靠一台引擎，天花板在哪

四台本地引擎，各自跑同一条录音，按同一把尺打分（461 个实质语义块里出问题的块数）：

```
FireRed-ASR2    95      AED 自回归
Paraformer      113     非自回归
Zipformer-CTC   114     CTC 逐帧
Qwen3-ASR       131     LLM 式
```

**最好的那台也有 95 处。**这就是「换个更好的模型」这条路的尽头 —— 排在后面的三台并不是
「更差的同类」，它们是**四种不同的架构**。这件事后面会变成整个方案的地基。

## 二、为什么是四种架构，不是同一台跑四遍

因为**同架构会一起错**。

自回归模型（一个字一个字往外吐）会在某一点崩掉然后复读；CTC 逐帧对齐的不会复读，
但对连读和吞音更钝；LLM 式的理解力强，但会「脑补」出通顺却没说过的话。
让它们听同一段，**错的地方不重叠**，投票才有意义。

拿数据说话。取每个规模下最好的组合，看「几台同时错」的块数：

```
1 台   95    FireRed-ASR2
2 台   62    + Zipformer-CTC      ← 第二台拿掉 33 处
3 台   52    + Qwen3-ASR            第三台再拿 10 处
4 台   48    + Paraformer-2023      第四台只再拿 4 处
```

**边际收益掉得很快。**第二台顶半边天，第四台几乎白搭。我们仍然默认跑四台，
是因为那 4 处里有内容、而代价只是时间 —— 但**「加引擎」不是一条可以一直走下去的路**。

那个 **48** 是天花板：这 48 个块四台一起听错，正确写法**根本不在选票上**。
任何「让模型从候选里挑」的方案都赢不过它。

## 三、融合：拿回了 41 处

四路 + 大模型融合 + 一份 10 条的行业术语库，实测 **54 处**。

```
可拿回的空间  95 − 48 = 47 处
实际拿回              41 处
离天花板还差           6 处
回退（四路都对、融合改错）  0 处
```

**零回退这条比「拿回 41 处」更重要。**它说明融合没有在瞎改 —— 一个会自作主张的融合模型，
能把分数刷上去，也能把本来对的改错，而后者用户是看不见的。

## 四、这里没有「对齐」这一步

线上那条生产线有一步 P2：把多家云端 ASR 的输出对齐到同一个时间轴上，再交给融合。
那一步有已知损失 —— 各家断句不同、时间戳精度不同，对齐本身会把证据切碎。

本机版**没有这一步**，因为不需要：

> 先做声纹分段和切块，**四台引擎吃的是同一份块**。所以第 N 块就是第 N 块，
> 对齐是恒等式。

这不是优化，是**顺序不同带来的结构性便宜**。云端做不到是因为各家 API 只接受整段音频、
自己决定怎么断句；本机做得到是因为切块在我们手里。

## 五、块边界比你想的敏感

我们量过：把块边界抖动 **0.5 毫秒**（8 个采样点），184 个块里有 16 个的 CTC 结果变了、
191 个块里有 32 个的非自回归结果变了。

这条冷知识后来救了一个 bug。有一块，自回归引擎把一个语气词连吐了 104 次、吞掉整句话。
代码里有熔断器，检测到复读就重试两次 —— 但**重试是原样重跑**，注释写着「AED 系不确定，
重跑大概率就好了」。

实测：

```
原样第 1 遍  len=122   …嗯嗯嗯嗯嗯（×104）
原样第 2 遍  len=122   一个字不差
原样第 3 遍  len=122   一个字不差
```

**贪心解码是确定的。**原样重跑的成功率是零，那两次重试纯属白烧 CPU。改成挪窗口之后：

```
终点往外扩 50ms   ❌ 没用
两头各扩 50ms     ✅ 救回来了，内容与另外三路吻合
起点往外扩 120ms  ❌ 又跑飞了     ← 不是越大越好
```

所以重试变成了一张**实测出来的梯子**，不是一个能往上调的系数。两条规矩焊死在代码里：
**只往外扩不往里切**（往里切会丢音频），**扩多少按梯子来**（非单调）。

## 六、术语库：第四条信息源

融合只能在四路候选里挑，所以它赢不过那个 48。**术语库违反了这个前提** —— 它不在四路里。

机制不是凭空造词，是**把音近的残缺候选锚回正确词形**：一个没听过的专名，三路整段听成了
读音相近的常见词（音对、字错），剩下一路给出的是这个专名的音近残片。没有术语库时，
融合按票数办事、跟了那三路；库里有正确写法时，那一路的残片就有了落点。

**关键是那一路必须已经给出了音近的东西。**库负责定形，不负责无中生有。

也说它没用的时候。这次挂着库跑，库里明明有的词仍然错了或丢了：

```
库里有〈两字术语 A〉   终稿写成了一个同音的常见单字
库里有〈两字术语 B〉   终稿写成了一个音近的日常词
库里有〈四字产品名 C〉 终稿把它整个丢掉了
```

而且它**不单调**：我们见过库里有那个词、融合反而写错的反例。**写错的词形会被模型当权威照着改
—— 写错比不写更坏。**

## 七、判分口径决定一切

同一份终稿，不同口径能差一倍多：

```
最严（语气词、数字体例、的地得全算，标了存疑也算）   76 处
最宽（只算真错真漏，标了存疑的豁免）                31 处
```

**所以「我们做到 X 处」这句话，脱离口径就是没有信息量的。**这也是我们把判分工具
放进仓库的原因 —— 不是大方，是这句话本来就不该由我们单方面说了算。

中间还踩了一个值得写下来的坑。判据第一版用「整句相似度 ≥ 0.88」当通过线，结果：

> 一个两字术语被听成了一个同音的常见单字，夹在三十多字的长句里，
> 整句相似度仍有 0.9+ —— 被判成「一致」放过了。

**相似度阈值会让自家产品看起来比实际好。**改成「归一之后金标那句必须原样出现在机器稿里」，
一个实词的差别就是一个实词的差别。

## 八、两条不能互套的经验

最后那步定字用大模型，云端 API 和本机开源模型都支持，同一条代码路径。但两边的调法**相反**：

- **云端那档要开推理**：`reasoning_effort: high`。实测比默认档**更快**（一批 102 秒 vs 334 秒），
  也更准 —— 想清楚了就不反复试探。
- **本机小模型要关思考**：Qwen3 系默认开思考模式，不关会先生成一大段推理，慢且没收益；
  实测开思考比不开**改得更多、错得更反**。

同一个词「思考」，在两个尺度上是两件事。**参数量才是杠杆，思考不是。**
