# 线上 → 本地 同步台账

本地版以线上 SaaS 仓为底本（Duner 2026-09-14 定）：线上代码整块拿，只换底座。

- **登记表只有一份：[`sync/saas.yaml`](../sync/saas.yaml)。** 线上每个文件拿不拿、改不改、为什么改，都写在那里。
  本文不抄那些理由，免得两份各改各的。
- **本文写的是怎么跟：** 什么时候跑巡检、结果怎么读、跟上之后怎么挪基线，以及每次巡检的记录。
- 做法照线上仓自己跟研究仓同步的那一套（线上 `server/pipeline/sync-check.sh` + `docs/vendor-sync.md`）。

## 纪律

1. **只改本仓，不改线上仓。** 发现线上的问题，记下来交给线上自己改。例如删除转录报 500 那条，见 CLAUDE.md 远期待办。
2. **线上更新后先跑巡检**，动登记为 `same` 的文件之前也先跑。
3. **本地要改一个 `same` 文件：先在 saas.yaml 把它登记成 `modify`，写清改什么，再动手。**
   否则下次 `saas_pull` 会把本地改动原样覆盖掉；巡检也会把它报成「未登记差异」。
4. **线上的新内容一律走 `saas_pull` 拿进来。** 它先过敏感扫描，要用内部仓的私有词表。巡检只比内容、不扫描。

## 跑

```bash
python3 tools/saas_sync_check.py      # 线上仓默认在 ../Transcribe.solution，别处用 --saas 或 TRANSCRIBE_SAAS
```

退出码：0 = 没有预期外的差异；1 = 有要处理的；2 = 读不了线上仓。

**基线**是 `sync/saas.yaml` 里的 `base:`，指上次跟上线上时线上仓的那个提交。
巡检拿线上现在的内容跟基线比，才分得出一处差异是「线上改过」还是「本地改过」。
线上仓还没提交的改动也算「线上改过」。

## 结果怎么读

| 标记 | 意思 | 怎么办 |
|---|---|---|
| `[已登记]` | 登记为有意不同，和线上不一样 | 预期内，不用管 |
| ⚠️ 未登记差异 · 线上改过 | 登记为原样同步，线上改了 | 跑 `saas_pull` |
| ⚠️ 未登记差异 · 本地改过 | 登记为原样同步，本地改了 | 还原；真要改就先登记成 `modify` |
| ⚠️ 要合并 `[已登记]` | 登记为有意不同，线上自基线后又改过 | 看线上改了什么（`git -C <线上仓> diff <基线> -- <线上路径>`），人工合进本地版 |
| ⚠️ 缺文件 | 登记为要拿，本地没有 | 多半是线上新加的：跑 `saas_pull` |
| ⚠️ 未登记文件 | 登记表一条规则都没匹配上 | 在 saas.yaml 加一条，决定拿不拿 |
| ⚠️ 线上删了 | 基线时线上还有，现在没了，本地还留着 | 本地一并删掉 |
| 提示 · 与线上一致 | 登记为有意不同，内容却和线上一样 | 不影响同步；确定以后也不改的，可以改回 `same` |

## 跟上线上的一轮

1. `python3 tools/saas_sync_check.py`：看线上自基线改过几个文件，各落在哪一类。
2. `TRANSCRIBE_SCAN_WORDS=<内部仓私有词表> python3 tools/saas_scan.py`：线上新加的文件先登记，新加的内容先过扫描。
   要做到未登记 0、待看 0。
3. `TRANSCRIBE_SCAN_WORDS=… python3 tools/saas_pull.py --part backend`，再跑一遍 `--part frontend`：
   `same` 覆盖，`modify` 本地已有就不动。
4. 「要合并」的逐个人工合。
5. `python3 tools/saas_pp_prompts.py --check`：后处理提示词在线上 vendor 目录里，登记为不拿，巡检看不到它，所以单独查。
   报「改过了」就去掉 `--check` 重新生成。
6. 跑全部测试（命令见 CLAUDE.md），界面有改动的在浏览器里走一遍。
7. 巡检只剩 `[已登记]` 之后，跑 `python3 tools/saas_sync_check.py --mark-synced`，把基线挪到线上当前提交，
   和这一轮的改动一起提交。
   - 还有未处理的项时，这一步会拒绝。
   - 线上仓有没提交的改动时，这一步也会拒绝。
